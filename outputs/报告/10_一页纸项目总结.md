# 优惠券精准投放与增量效果评估

**Starbucks Promotions 公开数据策略分析｜业务型数据科学 / 增长策略 / 数据分析**

## 一句话

这个项目不回答“谁最可能买”，而是回答“谁是因为券才买”：用 30 天公开数据还原“分层 → 发券 → 增量评估 → 预算 → 监控”闭环，核心结论是 **完成率不等于增量净额**。

## 数据

- 17,000 用户、306,534 条事件、76,277 次发券、10 种券、30 天活动窗口。
- 事件：交易 138,953；发券 76,277；查看 57,725；完成 33,579。
- 发券前特征严格截断，避免用未来信息；模型按用户切分，避免同用户泄漏。

## 方法链

1. **人群分层**：RFM/行为特征 → 价值维 3 档 × 行为维 4 档 → 9 个实际人群。
2. **策略矩阵**：9 人群 × 6 券型，输出完成率、每千次净 GMV；识别高价值·全响应 4,832 人完成 51% 的券、消耗 53% 的补贴。
3. **响应模型**：LightGBM 预测“收到券后是否完成”，AUC 0.866、PR-AUC 0.876、top 10% lift 1.76；只做人群内排序，不回答“发不发”。
4. **增量评估**：信息型券作同触达、无购买激励的准对照，用户固定效应吸收稳定画像；72h 购买率 +2.36pp、GMV +1.48 元/次；168h +3.92pp、+6.16 元/次（含后续触达，只作上界/敏感性）。
5. **预算策略 v2（回溯上限）**：只给高价值·全响应、中价值·全响应发 d7，其余发信息型；期望核销补贴 7.23 万、增量 GMV 19.19 万、增量净额 11.96 万、ROI 2.66。人群标签发券时不可得，不能直接上线。
6. **实验与监控**：5,542 人分层 A/B 方案；PSI、模型衰减、券效、数据量监控。

## 核心结论

| 口径 | 结果 | 说明 |
|---|---:|---|
| 03 S1 账面净额 | +16.8 万 | 把“信息型本来就会买”算成券的功劳 |
| 05 同口径重算 S1 | −3.08 万 | 只算券相对信息型的增量，补贴用 03 实际核销 41,959 |
| v2 增量净额 | +11.96 万 | 期望核销补贴 7.23 万，ROI 2.66；回溯上限 |
| 响应模型 AUC | 0.866 | 排序好，不等于增量 |
| 72h 增量 | +2.36pp | 用户 FE，准实验 |
| A/B 合并 MDE | 3.19 元 | 观测差 5.16 元，power 99.5% |

一句话解释：**按完成率发券，会把预算花在本来就会买的人身上；按增量净额发券，才是在为“券带来的额外购买”付费。**

## 工程化

- `src/run_all.py`：10 步一键复现，本机实测约 5 分钟；07→09 约 16 秒。
- `tests/`：9 项关键结果回归测试，当前全过。
- `sql/`：9 条 Spark SQL 兼容查询，DuckDB 本地执行，34 项对账全过。
- 监控：分数 PSI 0.06、画像特征约 0；行为历史 PSI 高，定位为 30 天窗口回看长度伪影，不直接判漂移；监控期 AUC 0.864→0.879，d7 每发送净 GMV 22.81→28.03。

## 边界（面试要主动说）

- 05 是观测数据准实验，不是严格 RCT；不说“证明因果”。
- 预算 v2 是回溯性上限测算，不是可上线人群规则；人群标签来自全窗口行为，下一步是小流量 A/B，当前没有线上实验。
- A/B 是方案与功效计算，不是线上 A/B；对照是信息型，不是不触达。
- 监控是 30 天历史离线回放，不是生产实时监控。
- SQL 用 Spark SQL 兼容写法，DuckDB 本地验证；未上 Spark 集群。

## 面试 60 秒版

> 这个项目分析优惠券精准投放。我先用 RFM + 行为双聚类分出 9 个人群，再用 LightGBM 做响应排序；但响应模型只能回答“先发给谁”，不能回答“发不发”。所以我把信息型券当准对照，加用户固定效应做增量评估，发现整体 72 小时购买率只提升 2.36 个百分点。把增量代进预算后，只给两个全响应人群发 d7，期望核销补贴从 16.5 万降到 7.2 万，增量净额 11.96 万、ROI 2.66。但这是回溯上限，人群标签发券时拿不到，不能直接上线，下一步要做小流量 A/B。最后补了 SQL 对账、A/B 样本量和 PSI/模型衰减监控，并用 run_all + 回归测试保证可复现。
